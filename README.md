# Фонд оценочных средств: «Управление ИИ-разработкой AI-продукта»

Открытый фонд оценочных средств проектного модуля, в котором команда из
четырёх человек за семестр доводит продукт с ИИ внутри до публичного
адреса и защищает его перед людьми.

Материалы курса, лабораторные и галерея прошлых проектов —
[sii.sergeivolchkov.ru](https://sii.sergeivolchkov.ru).

## 1. О модуле

**Цель.** Научить делать продукт с ИИ внутри так, чтобы им можно было
пользоваться и чтобы за качество можно было отвечать цифрами. Не «изучить
нейросети», а пройти путь от чужой боли до работающего решения, о котором
известно, где оно врёт.

**Задачи.** Собрать команду с разделением ответственности; довести продукт
до публичного адреса; научиться мерить качество работы ИИ и защищать
измерения; отвечать за решения в разговоре, а не в отчёте.

**Структура.** Семь модулей на шестнадцать недель, сквозной командный
проект. Каждый модуль заканчивается приёмкой: работа сдаётся pull request,
проверяется по критериям, затем команда защищает её в разговоре с
преподавателем.

**Пререквизиты.** Python на уровне скрипта, ходящего в чужой API, git с
ветками и pull request, основы HTTP и SQL, представление о том, что такое
метрика качества и переобучение. Конкретные фреймворки, Docker и работа с
языковыми моделями разбираются по ходу.

Требования расписаны через умения, а не названия дисциплин, и снабжены
пятью вопросами для проверки группы — [входные
требования](docs/rpd.md#2-входные-требования). Там же сказано, куда модуль
ставить нельзя.

**Планируемые результаты.** По завершении обучающийся способен:

1. сформулировать задачу продукта через боль конкретного пользователя и
   проверяемый критерий успеха;
2. спроектировать систему вокруг готовой модели и обосновать выбор
   архитектуры, включая цену принятых решений;
3. довести решение до публичного адреса со сборкой, развёртыванием и
   наблюдаемостью;
4. измерить качество работы модели на собственном наборе данных и
   объяснить, где решение ошибается;
5. проверить устойчивость продукта к недоверенному вводу и описать
   поверхность атаки;
6. защитить работу в живом разговоре, отвечая за каждое решение.

## 2. Роли и связь с компетентностно-ролевой моделью

Команда — четыре роли, каждая сдаёт свои артефакты своим pull request и
отвечает за свою часть на приёмке.

| Роль модуля | Зона ответственности | Ближайшая роль КРМ |
|---|---|---|
| Product / Vision Owner | Какую проблему решаем, что считается хорошим решением, приёмка | **AI PM** |
| AI Engineer | Как продукт использует модель и почему именно так | ML Engineer, частично AI Architect |
| Delivery Engineer | Сделанное командой работает на публичном адресе | AI Architect в части внедрения |
| AI Quality & Safety | Чем меряется качество и держит ли продукт атаку | прямого соответствия в КРМ нет |

Две роли выходят за рамки модели компетенций: вывод в эксплуатацию и
безопасность LLM-продукта. Это следствие фокуса — модуль про продукты
вокруг готовых моделей, а не про обучение своих.

Результаты обучения сопоставлены с компетенциями и индикаторами КРМ 3.0 —
см. [docs/competency-map.md](docs/competency-map.md).

## 4. Что отличает эту оценку

**Критерии существуют как код.** Каждый из 104 критериев — запись с
идентификатором, весом и способом проверки: запуск команды, поиск
артефакта, структура репозитория, живой URL, экспертная оценка по тексту
работы, разговор на приёмке. Студент видит их до начала работы.

**Два слоя проверки, и они разные.** Балл считается по критериям и виден
всем. Приёмка — булевая: принято или не принято, торга за полбалла нет.
Не принято — оценки нет, сколько бы баллов ни набралось.

**Проверка формы отделена от проверки понимания.** Есть ли артефакт,
запускается ли система, работает ли публичный адрес — проверяется
машинно. Понимает ли студент, что сделал, — только в разговоре, и для
этого у каждого критерия есть вопрос к защите.

Подробнее — [docs/assessment-model.md](docs/assessment-model.md).
